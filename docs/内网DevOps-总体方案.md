**三条硬结论：**

1. **Codes 与禅道功能高度重叠**（需求池/任务/缺陷/用例四件套都有）→ **必须二选一**，否则又回到「信息分散」的老问题。
2. **Zadig 不做需求/缺陷/用例**（官方定位：项目管理交给 Jira/Tapd/PingCode/飞书，自己只做交付）→ 它不能替代禅道或 Codes。
3. **Zadig 的核心价值是 k8s 多服务编排 + 蓝绿/灰度/环境隔离**，而当前主线是 **Electron 桌面应用**（产物是 exe，部署=发安装包）→ **Zadig 在当前项目上价值很低**。

## 3. 三个必须现在拍的决策

### D1｜需求 / 缺陷 / 用例 用**禅道**还是 **Codes**？（二选一）

| 维度 | 禅道 21.7.9 | Codes 3.7.0GA |
|---|---|---|
| GitLab 集成 | ✅ **原生，已打通**（代码库页签、commit 写 `Bug #1` 自动关联并流转） | ❌ 无（只有 Jenkins 型 CI 配置） |
| 测试管理 | ✅ 用例库 + 测试单 + 测试报告 + Bug 流转，最完整 | ✅ 用例双库，但测试执行/报告弱 |
| 界面 / 上手成本 | ❌ 老派，需 30 分钟培训 | ✅ 现代，类飞书，几乎零培训 |
| 工时 / 日报 / 大屏 | 有，较基础 | ✅ 强（含逃逸率、冒烟通过率） |
| 数据位置 | ✅ 全本地 | ⚠️ 程序本地、**认证在云端**（需 icodes.work 租户） |
| 定制 / 二次开发 | ✅ 开源可改（已改过 model.php 补丁） | ❌ 闭源 |
| 迁移成本（从腾讯文档） | 需求批量创建、用例 CSV/XMind 导入 | 支持「禅道/Jira/itest 一键搬家」，但不支持从表格导 |

**推荐：禅道。** 理由三条：
1. **GitLab 关联是刚需**（开发不用打开禅道，commit 里写 `Fix Bug #12` 就自动流转，这是大厂 smart commit 同款机制），Codes 做不到；
2. 测试用例/测试单/报告是**腾讯文档最缺的**，也是这次迁移的最大收益点，禅道这块最完整；
3. 数据全本地、可改代码，符合内网合规与长期可控。

**Codes 保留为备选**：若团队试用两周后普遍抵触禅道界面，再切 Codes，代价是放弃 GitLab 原生关联（需要保留我写的那条桥来补）。

### D2｜Zadig 怎么定位？

**现状**：Zadig 5.0 已装好（17 个 pod），但和 GitLab Runner 的「构建」能力重叠，而它的强项（k8s 多环境/灰度/环境隔离）对桌面应用用不上。

**三个选项：**

| 选项 | 说明 | 适用 |
|---|---|---|
| **A. 暂不接入（推荐）** | 保留容器与访问地址，主流程不依赖它。等后端服务上 k8s 再启用 | 当前只有桌面端 |
| B. 只做「发布编排」 | GitLab CI 出包 → Zadig 拉产物 → 部署到多环境 k8s + 审批 | 已有 k8s 后端服务 |
| C. 全面替代 GitLab CI | 构建也搬进 Zadig | ❌ 不建议：双份维护，且 Zadig 构建对 wine/NSIS 支持不如现成镜像 |

**推荐 A**，并在方案里写明「什么条件下切 B」：当出现 **≥2 个后端服务需要部署到 k8s 多环境** 时，Zadig 才开始产生价值。

---

### D3｜腾讯文档的边界

**不替换，只分工**：

| 内容 | 去哪 |
|---|---|
| 需求方案、原型说明、会议纪要、验收记录、周报 | **腾讯文档**（继续用） |
| 需求条目、Bug 条目、测试用例条目 | **禅道**（要状态、要关联、要统计的东西） |

判断标准一句话：**需要"状态流转"或"被统计"的，进禅道；只需要"被阅读"的，留腾讯文档。**

### 一条需求的生命周期（目标态）

1. **产品**在腾讯文档写方案 → 评审通过后在禅道建「需求」
2. **开发**在 GitLab 建分支 → 提交时写 `Story #12` → 禅道需求页签出现提交记录
3. **CI** 构建出 exe → 上传 Package Registry
4. **测试**在禅道建「测试单」，执行用例；发现问题提「Bug」，指派给开发
5. **开发**修复 → 提交写 `Fix Bug #23` → **Bug 自动转「已解决」并挂上提交**
6. **测试**验证通过 → 关闭 Bug；**发布**打 tag → CI 出正式包 → Release
7. **老板**看禅道效能看板：需求交付周期、Bug 趋势、用例通过率

## 5. 分阶段落地

| 阶段 | 内容 | 验收标准 | 预估 |
|---|---|---|---|
| **P0** | 现状固化：GitLab CI + 产物 + Release 已通 | ✅ 已完成（v0.2.9） | — |
| **P1** | 禅道 commit 关联跑通 | 提交 `Fix Bug #1` → Bug 自动变「已解决」并显示提交 | 0.5 天 |
| **P2** | 快速导入工具（腾讯文档 → 禅道） | 一份真实 Excel 导入成功，需求/Bug/用例各 ≥10 条 | 1 天 |
| **P3** | 小范围试点（1 测试 + 1 产品） | 一个完整迭代走完禅道流程 | 2 周 |
| **P4** | 部署形态升级（可选） | 禅道上 k8s（外部 MySQL + PVC + 多副本）或 外部 MySQL + 定时备份 | 按需 |

> **P4 单独说明**：当前禅道是 `docker run` all-in-one（应用+MySQL+Redis 一个容器）。官方镜像支持外部数据库（`MYSQL_INTERNAL=false` + `ZT_MYSQL_HOST` 等环境变量），但**官方没有 Helm chart**，上 k8s 需要自己写 Deployment/StatefulSet + PVC。
> 若只是担心「单机挂了数据丢」，**不需要 k8s**：外部 MySQL + 定时备份 + `restart always` 就够，成本低一个数量级。

## 7. 运维脚本的自管理（ops/zentao-bridge）

禅道原生只能「从 GitLab 拉 Issue」，不能反向建。补这一环的桥脚本**不放服务器上散着**，而是纳入本仓库，由 GitLab CI 部署 —— 即「GitLab 管 GitLab 自己的运维脚本」。

| 关注点 | 做法 |
| --- | --- |
| 源码 | `ops/zentao-bridge/bridge.py`（约 200 行，仅标准库） |
| 进程 | 宿主 systemd `zentao-bridge.service`（`Restart=always`），监听 8099 |
| 部署 | CI 作业 `deploy-bridge`（dev 分支、`ops/zentao-bridge/**` 有改动时手动触发） |
| 重启 | 宿主 `zentao-bridge.path` 侦测 `/srv/zentao-bridge/bridge.py` 变化 → 触发 `zentao-bridge-reload.service`（oneshot `systemctl restart`） |
| 校验 | 桥启动时把自身源码 sha256 报在 `/health` 的 `source_sha256`，CI 轮询比对，一致才算部署成功 |
| 配置 | 禅道 `zt_webhook` + `zt_config(message.setting)`，一次性写库 |

踩过的两个坑（都已修）：

1. **path 单元不能直接指向业务服务** —— 服务已在跑时 path 触发执行的是 `start`，等于空操作，新代码不会加载。必须指向 oneshot 的 restart 单元。
2. **健康检查会骗人** —— 老进程应答 `/health` 也是 200。所以用「启动时缓存源码哈希」+ CI 轮询比对来证明新代码确实被加载。

验证记录（2026-11-19）：v1.1.0 → 1.1.1 → 1.1.2 三次部署均由 CI 完成，pid 每次都换；禅道提交 Bug #3 后 1 秒内 GitLab 出现 Issue #2（labels `zentao,bug`，正文含字段表与禅道回链）。
